Map Format

Originally Doom 64 maps were separate WADs within the main WAD which helped with compression purposes. Each map contains 14 lumps, in specific order, which describe the map geometry, behavior, and contents. The format is the same for the Nintendo 64 engines and the PC engines, except the PC versions use number hashes for textures (see Texture Hashing). All numbers are stored little-endian, and "int16" and "uint16" mean signed and unsigned 16-bit values. A "map unit" is one unit in the map editor. Heights and positions are plain whole numbers except for the vertices, which are 16.16 fixed point.

THINGS

Things are sprites that appear in game which can be enemies, projectiles, and decorations. Each thing takes up 14 bytes. There are no limits to the number of things but only 256 things can be shown at once on screen.

Offset Size Type Field Description
0 2 int16 x X position in map units.
2 2 int16 y Y position in map units.
4 2 int16 z Height offset in map units.
6 2 int16 angle Facing angle in degrees however the engine only uses multiples of 45.
8 2 int16 type Thing type (doom editor number).
10 2 int16 flags Things flags.
12 2 int16 tid Thing tag.

LINEDEFS

Line definitions (linedefs) define sector edges, walls, and sometimes activation points. Each linedef is 16 bytes. A maximum of 32,768 (524,288 bytes) linedefs are allowed.

Offset Size Type Field Description
0 2 uint16 v1 Index of the start vertex.
2 2 uint16 v2 Index of the end vertex.
4 4 uint32 flags Line flags.
8 2 uint16 special Activation type (specials).
10 2 int16 tag Linedef tag.
12 2 int16 sidenum[0] Index of the front (right) sidedef. Every line has one.
14 2 int16 sidenum[1] Index of the back (left) sidedef, or −1 (0xFFFF) if the line is one-sided.

SIDEDEFS

Sidedefs store texture references, offsets, and sector reference. Each sidedefs is 12 bytes. A maximum of 32,768 sidedefs (393,216 bytes) are allowed.

Offset Size Type Field Description
0 2 int16 textureoffset Horizontal texture offset in map units.
2 2 int16 rowoffset Vertical texture offset in map units.
4 2 uint16 toptexture Upper texture index or hash (PC).
6 2 uint16 bottomtexture Lower texture index or hash (PC).
8 2 uint16 midtexture Middle texture index or hash (PC).
10 2 int16 sector Index of the sector this side faces.

VERTEXES

Vertexes are map locations that linedefs and segs use for referencing. They are 8 bytes each. A maximum of 32,768 vertexes (262,144 bytes) are allowed.

Offset Size Type Field Description
0 4 int32 x X coordinate in 16.16 fixed point (divide by 65536 for map units).
4 4 int32 y Y coordinate in 16.16 fixed point (divide by 65536 for map units).

SEGS

A seg os a piece of a linedef created by the node builder when the map is split into subsectors. Each seg is 12 bytes. A maximum of 32,768 segs (393,216 bytes) are allowed.

Offset Size Type Field Description
0 2 uint16 v1 Index of the start vertex.
2 2 uint16 v2 Index of the end vertex.
4 2 uint16 angle Direction of the seg as a 16-bit angle (65536 = 360°).
6 2 int16 linedef Index of the linedef this seg belongs to.
8 2 int16 side 0 if it belongs to the linedef front side and 1 for linedef back side.
10 2 int16 offset Distance along the linedef to the start of the seg in map units.

SSECTORS

Subsectors are convex pieces of a sector used for rendering. Each subsector is 4 bytes. The number of subsectors must equal the number of leaves in LEAFS. A maximum of 32,768 subsectors (131,072 bytes) are allowed.

Offset Size Type Field Description
0 2 int16 numsegs Number of segs in this subsector.
2 2 int16 firstseg Index of the first seg. The segs of a subsector are stored one after another.

NODES

Nodes are the binary space partition (BSP) tree. Each node is one dividing line that splits an area of the map into two halves. Each nodes is 28 bytes. A maximum of 32,768 nodes (917,504 bytes) are allowed.

Offset Size Type Field Description
0 2 int16 x X of the partition line start in map units.
2 2 int16 y Y of the partition line start in map units.
4 2 int16 dx Partition line X direction.
6 2 int16 dy Partition line Y direction.
8 8 4 × int16 bbox[0] Bounding box of child 0 (right): top, bottom, left, right, in map units.
16 8 4 × int16 bbox[1] Bounding box of child 1 (left): top, bottom, left, right, in map units.
24 2 uint16 children[0] Right child: a node index, or a subsector index if bit 0x8000 is set.
26 2 uint16 children[1] Left child: a node index, or a subsector index if bit 0x8000 is set.

SECTORS

Subsectors define the rooms and areas of a map. Each sectors is 24 bytes. A maximum of 32,768 sectors (786,408 bytes) are allowed.

Offset Size Type Field Description
0 2 int16 floorheight Floor height in map units.
2 2 int16 ceilingheight Ceiling height in map units.
4 2 uint16 floorpic Floor texture index or hash (PC).
6 2 uint16 ceilingpic Floor texture index or hash (PC).
8 10 5 × int16 colors[5] Lights lump indices in order of floor, ceiling, thing, upper wall, lower wall.
18 2 int16 special Sector special.
20 2 int16 tag Sector tag.
22 2 int16 flags Sector flags.

REJECT

A table of which sector pairs can never see each other, used to skip line-of-sight checks. It has one bit per ordered pair of sectors, so its size is ceil(numsectors × numsectors / 8) bytes. This lump has a maximum of 134,209,537 bytes.

BLOCKMAP

A grid of 128×128 map unit blocks listing the linedefs in each block, used for collision. Each block has variable size. A maximum of 65,534 bytes is allowed.

Part Size Type Description
Header 8 bytes int16 Four values: originX, originY (map units, lower left corner of the grid), width and height (in blocks).
Offsets width × height × 2 bytes int16 One offset per block, row by row from the bottom. Each is the position of that block's list, counted in 16-bit values from the start of the lump.
Lists Variable int16 One list per block (blocks with the same contents can share a list). Each list is the linedef indices followed by −1. Blocks with no lines share a list that is only −1.

The whole lump is limited to 65,534 bytes because the offsets are 16-bit (see Maps).

LEAFS

One leaf per subsector, in subsector order, listing the vertices of its convex polygon in order. This is similar to the GL nodes of other engines. A leaf takes 2 + 4 × count bytes. The number of leaves must equal the number of subsectors. Only 3,072 vertexes from leaves can be drawn at once but there is no limit in lump size.

Part Size Type Description
count 2 int16 Number of vertices in the leaf.
vertex 2 int16 Vertex index (repeated count times, each followed by a seg).
seg 2 int16 Seg index that the edge starting at this vertex belongs to, or −1 (0xFFFF) if the edge is not part of a seg (a miniseg created by the node builder).

LIGHTS

These are custom colors referenced by the sector colour indices. Each light is 6 bytes which are numbered from 256 (indices 0–255 are the built-in greys). A maximum of about 32,500 lights (195,072 bytes) are allowed.

Offset Size Type Field Description
0 1 uint8 r Red.
1 1 uint8 g Green.
2 1 uint8 b Blue.
3 1 uint8 a Alpha (unused).
4 2 int16 tag Light tag.

MACROS

Macros are scripts which contain sequences of actions (linedef actions 256–511). The lump is a header followed by one block per macro. Macros vary in size and are limited to 256 macros in total and can only have a total (all macros) of 32,767 actions. The lump is limited to 198,654 bytes.

Lump Layout

Part Size Type Description
Header: nummacros 2 int16 Number of macros.
Header: numactions 2 int16 Total number of actions in all macros.
Macro block: count 2 int16 Number of actions in this macro. Repeated for each macro.
Macro block: action entries (count + 1) × 6 3 × int16 per entry count action entries followed by one end entry. Each entry is three values: id, tag and special.

Action Entry

Offset Size Type Field Description
0 2 int16 id Step number, usually in multiples of 10. Actions with the same id run together; the macro waits for a new id to continue (this is what the wait and delay keywords set up). An id of 0 ends the macro.
2 2 int16 tag Tag or argument for the action (may be negative).
4 2 int16 special Line action number.

The end entry that follows each macro's actions is stored in the file as all zeros. The engine never runs it, since an id of 0 ends the macro. When a macro is disabled by the macro toggle actions, its first id is stored as a negative number at runtime.

SCRIPTS (PC)

On maps made on PC, you will often find an additional lump called scripts. This is a text entry which has uncompiled scripts that are compiled with BLAM. This does not exist on the original Nintendo 64 maps.
